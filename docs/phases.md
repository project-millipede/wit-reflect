# Definitions and phases

**Status: Phases 1 to 9 implemented, 2026-11-23.**

The goal is the generation model required by the generator comparison:

```text
Existing Rust operations and types + declarative generation metadata
    -> Generated application WIT and required boundary adaptation
    -> wit-bindgen bindings, with compatible Rust type mappings
    -> jco / TypeScript bindings
```

wit-bindgen keeps the canonical ABI and jco the TypeScript side. This library
produces the WIT and, from Phase 4, the adaptation onto those bindings. From
Phase 6 it also produces the type mappings named in the third line.

## Definitions

| Term | Meaning |
| --- | --- |
| Owner type | The struct or enum the ordinary Rust implementation already uses. The only place a field is edited. |
| Reflection | `WitType::wit_type`, implemented by the derive in the owner crate. Rust has already resolved aliases, re-exports, dependency crates and generic arguments. |
| Type graph | Every named definition reached from declared types, identified by `TypeId`, in dependency-first order. |
| Instantiation | One concrete use of a generic owner type. Always its own definition. |
| Schema | The declaration of a package: interfaces, the types each defines, instantiation names. Built from the registry, or call by call in a schema program. |
| Mark | An attribute by which an item states its own part of the contract: `interface`, `#[exports(…)]`, `#[export(interface = …)]`, `#[named]`. (Phase 7) |
| Registration | What a mark submits at link time: a function that adds the item to a schema, and the item's source position. (Phase 7) |
| Contract settings | The `[package.metadata.wit-reflect]` table of the component crate: package, world, imports, exports, and functions the component crate implements itself. (Phase 7) |
| Placement | The rule giving each named type exactly one owning interface; other interfaces `use` it. |
| Wire type | The Rust type whose reflection defines what crosses the boundary for a field. Without a rule or a map entry it is the field's own type. |
| Representation rule | A `#[wit(...)]` attribute naming a field's wire type and how it is obtained: one pair of wire type and conversion. It drives both the WIT and the generated lowering. It is written on the field, or on the type for several fields at once. |
| Representation map | A type of the owner crate, declared with `representations!`, that states once how each type of another crate is shown. Every field without a rule is looked up in it. (Phase 9) |
| Shown type | The right-hand side of a map entry `Foreign => Shown`: the wire type for every field of type `Foreign`, obtained with `From`. `DisplayText` is the shown type for a value's `Display` text. (Phase 9) |
| Computed field | A field of the wire record with no stored counterpart, produced by a function of the whole value. |
| Wire parts | An owner value taken apart in declaration order with every rule applied: a field list for a record, a nested choice for an enum. Parts contain no binding types. |
| Lowering | `Lower::lower`, generated by `#[derive(WitType)]` in the owner crate, where private fields and rule functions are accessible. |
| Assembly | `FromParts`, derived on wit-bindgen's types through `additional_derives`. It builds a binding value from parts by position. |
| Forwarding file | Generated Rust source implementing the binding traits of a world's exported interfaces. |
| Bindings file | Generated Rust source defining `generate_bindings!`: `wit_bindgen::generate!` with the world, the assembly derive and the type mappings filled in. (Phase 6) |
| Unchanged type | An owner type the bindings use themselves through wit-bindgen's `with`. Its values are moved, not converted. (Phase 6) |
| Converted type | Every other owner type: taken apart into wire parts and assembled into the binding's own type. |
| Passage | `Lower::Passage`, either `Unchanged` or `Converted`. The compiler computes it from the type and its field types. (Phase 6) |
| Resource cell | `ResourceCell<T>`, the type a component registers for a resource. It gives `&mut self` methods access from WIT methods. |
| Generated artifacts | The WIT file, the bindings file and the forwarding file. Outputs of one contract, committed, never edited by hand. |
| Remote declaration | A local declaration of a foreign type's shape, marked `#[wit(remote = path)]` and checked by a generated exhaustive `From`. |
| Adaptation | Generated lowering from owner values to wit-bindgen binding values. (Phase 4) |
| Forwarding | Generated `Guest` and resource implementations that call the ordinary Rust operation. (Phase 4) |
| Resolved package | The validated result of a schema. Only this can be rendered. |
| Operation | A Rust function or method that is exported: named in `#[exports(…)]` on its `impl` block, or marked with `#[export]`. The mark adds a hidden companion that reflects its signature; `#[exports(…)]` applies it to the functions it names. |
| Operation reference | `operation!(Session::inspect)`: names that companion in a schema program. |
| Root | An item that states an interface: a function of an interface, or a type or resource that nothing else places. Everything a root mentions follows it. |
| Resource | A Rust type exported as a WIT `resource` with `#[derive(WitResource)]`. By value it is `own<r>`, behind a reference `borrow<r>`. |
| External interface | An interface of a pinned dependency. Types placed there are imported with `use`, never defined locally. |
| World | Named imports and exports. A target is a declared interface or an external interface path. |

## What each generator contributed

| Capability | Source of the idea | What this library adds |
| --- | --- | --- |
| Compiler-resolved type reuse and generic carriers | Witty: derive plus trait registration | No layout or ABI bounds on the owner derive, only `T: WitType`. |
| Distinct instantiations | None of the three (first-wins, or arguments lost) | `TypeId` identity, a collision error, declared instantiation names. |
| Aliases, re-exports, dependency types, `cfg_attr` | None | A consequence of reflection instead of source scanning. |
| Keyword-safe names such as `%result` | WITGenstein, Fidius | One keyword table applied to every identifier position. |
| Struct-like case payload records | Fidius | A declared name, or one derived from the resolved variant name. |
| Cross-interface type use | None | The placement rule and generated `use` lines. |
| Failure detection | Fidius: errors for unsupported types | All diagnostics aggregated; compile-time rejection with tailored messages. |
| Resources with constructors | WITGenstein | Free factory returning `own<r>`, methods from several `impl` blocks, `&mut self`. |
| Deliberate method selection | None (WITGenstein exports every inherent method) | `#[exports(…)]` names the exported functions of an `impl` block. Nothing follows from `pub` or from the block's layout. |
| Declared error types in results | None (Fidius substitutes its framework error) | `Result<T, E>` is reflected as declared. |
| World and export naming | Witty (configurable names) | Named exports, external imports and external `use`. |
| Generated conversions and guest glue | Fidius | Generated against owner types, not an author model. (Phase 4) |
| Semantic projections | None | Representation rules: `display`, `into`, `with`, `skip`, computed fields. `usize` is widened without a rule. |
| Compatible Rust type mappings | wit-bindgen's `with`, written by hand in the workbench | Generated, and decided per type by the compiler instead of declared. (Phase 6) |
| Types of other crates | None (Fidius and WITGenstein cannot see them; Witty needs its derive on them) | Remote declarations checked by the compiler, and a map that states each foreign type's representation once per crate. |
| Declaring the contract | Witty and Fidius: a separate declaration or author model | Marks on the items and settings in `Cargo.toml`; no schema program. (Phase 7) |

## Phases

Each phase ends with formatting, Clippy, tests, a status update here and a review.

### Phase 1 — Type reflection (done)

Owner types to validated WIT type definitions.

- `WitType` for primitives, `String`, `Vec`, `Option`, `Result`, `Box`, tuples, `()`.
- Derive: records, enums, variants, payload records, transparent newtypes,
  declared names, doc comments, generic parameters.
- `Schema`, placement, naming, aggregated `SchemaErrors`, deterministic rendering.

Evidence: `crates/wit-reflect/tests/type_reflection.rs`.

| Test | What it establishes |
| --- | --- |
| `generic_owner_types_render_the_handwritten_contract` | Two instantiations through Rust aliases, nested `%result`, payload record and cross-interface `use` equal the handwritten text. |
| `rendered_package_is_accepted_by_the_wit_parser` | That text is valid WIT for `wit-parser` 0.261. |
| `unnamed_instantiations_of_one_generic_type_are_rejected` | Instantiations are never merged. |
| `undeclared_type_shared_by_two_interfaces_is_rejected` | Placement is never arbitrary. |
| `recursive_types_are_reported` | Reflection terminates on recursive types. |

Against the acceptance criteria: criterion 1 (direct type reuse) is met for type
definitions; the type half of criteria 2 and 4 follows from it. Nothing has been
run against the workbench's real `Session::inspect` types yet.

### Phase 2 — Operations and worlds (done)

The complete WIT contract from real Rust signatures.

- `#[export]` on functions and methods; `operation!` to select them.
- `#[derive(WitResource)]`; methods, static functions and constructors;
  `own` and `borrow` handles from the Rust signature.
- `Schema::external_interface` for types a dependency defines.
- `Schema::world` with imports, exports and named exports.
- Types used only in a signature are placed by the Phase 1 rule.

Evidence: `crates/wit-reflect/tests/operations.rs`.

| Test | What it establishes |
| --- | --- |
| `session_operations_render_the_handwritten_contract` | Listed methods from two `impl` blocks, `%resource: string` from `&str`, the factory's `own<session>`, a signature-only type, the external `use` and the world equal the handwritten text. Unlisted and unmarked methods are absent. |
| `rendered_contract_is_accepted_with_its_dependencies` | That text resolves in `wit-parser` 0.261 together with its two dependency packages. |

Against the acceptance criteria: criterion 2 (complete WIT generation) is met for
a contract whose operations map one-to-one to Rust functions. It has been shown
on fixtures shaped like the workbench contract, not on the workbench crates.

Limits:

- One Rust function maps to one WIT function. The production `open-file`, which
  calls `select_child(.., File)`, needs an ordinary Rust method first.
- `async fn`, consuming `self`, generic functions, `impl Trait`, `&mut`
  parameters and reference results are rejected at compile time.
- A type placed in an external interface is not compared with that interface's
  WIT. A mismatch surfaces when bindings are compiled.
- A handle nested in a borrowed container, such as `&[Session]`, stays `own`.

### Phase 3 — Representation rules (done)

The wire shape of fields that cannot cross the boundary as stored. The contract
follows the Rust types; rules bridge representation gaps only.

| Rule | Wire type |
| --- | --- |
| `#[wit(display)]` | `string` |
| `#[wit(widen)]` | `u64` for `usize`, `s64` for `isize` |
| `#[wit(into = W)]` | `W`'s representation, with `W: From<FieldType>` |
| `#[wit(into = W, with = function)]` | `W`'s representation, from `function: fn(&Self) -> W` |
| `#[wit(skip)]` | none |
| `#[wit(field(name = "…", into = W, with = function))]` | a leading computed field |
| `#[wit(cases = "…")]` | an enum with computed fields as a record of its cases |
| `#[wit(remote = path)]` | a checked local declaration of a foreign type |

Each rule's requirement is a trait bound of a function in `wit_reflect::rule`,
so an unsatisfiable rule is a compile error at the field.

Evidence: `crates/wit-reflect/tests/representation_rules.rs`.

| Test | What it establishes |
| --- | --- |
| `ruled_owner_types_render_their_declared_wire_shapes` | Every rule produces its declared wire type for owner types that use a foreign module without derives: `remote`, `into`, a sibling-dependent `with`, `display`, `widen`, `skip`, and a computed message on a struct and on an enum. |

Against the acceptance criteria: the schema side of criterion 3 (representation
and contract preservation) is met on fixtures. Complete messages and ordered,
typed diagnostics are kept; their nesting follows the Rust types.

#### Lowering spike

Before the rules were implemented, an uncommitted spike lowered one value per
rule onto bindings generated by wit-bindgen 0.60. It is not part of the
repository; these are its findings.

Verified:

- `additional_derives` applies a custom derive to generated records, variants
  and enums.
- A positional protocol works without naming binding types in owner crates.
  The owner side yields its wire parts in declaration order; the derived
  binding side assembles records from a field list and variants from a nested
  choice. Neither side has an arity limit.
- Every rule lowers: `display`, `widen`, `into`, `with` (evaluated before the
  fields are moved), `skip`, a computed field on a struct and on an enum, and
  a remote enum. So do `Option`, `Vec` and `Result` nesting, struct-like case
  payloads and generic carriers through an alias.
- The whole adaptation of an operation result is one call. The crate builds for
  `wasm32-unknown-unknown` and packages with `wasm-tools component new`.

Not verified:

- Resources, handles and generated `Guest` forwarding.
- Lifting of parameters, and import-side bindings.
- Coexistence with wit-bindgen's `with` remapping.
- Running the component, in Wasmtime or through jco.

Finding for Phase 4: when one nested conversion is missing, the compiler reports
only that the outermost binding type's bounds are not satisfied. The protocol
needs a per-field check or a tailored diagnostic.

Limits:

- A rule determines the generated WIT only. No value is converted yet.
- `From` impls and `with` functions for wrapped foreign numbers are written by
  hand, a few lines per foreign type.
- `with` applies to struct fields, not to fields inside enum cases.
- A foreign type with private fields, or a `#[non_exhaustive]` foreign enum,
  cannot have a remote declaration.

Derived by reading the workbench crates; applied in Phase 5.

| Contract part | Compared with the handwritten WIT |
| --- | --- |
| Report graph: `report`, `image`, `cpu-identity`, `macho-value`, ranges, platform, signature | Same shape. |
| `analysis-error { message, kind }`, `error-kind`, `truncated-range`, `failure { kind, message }` | Same shape. |

### Phase 4 — Adaptation and forwarding (done)

The code behind the contract: result conversion and the binding trait
implementations.

- `#[derive(WitType)]` also implements `Lower`, from the same plan as the
  schema, so the WIT and the conversion cannot disagree about a field.
- `#[derive(FromParts)]` assembles wit-bindgen's records, variants and enums.
- `ResolvedPackage::forwarding(world)` renders the forwarding file.
- `ResourceCell<T>` backs resources; `#[export]` and `operation!` record the
  receiver, by-reference parameters and the operation's Rust path.
- `fixtures/session`: an owner library and a component made only of generated
  artifacts, with a `generate` binary and its `--check` mode.

Evidence:

| Test | What it establishes |
| --- | --- |
| `committed_artifacts_are_what_the_schema_generates` (`fixtures/session/owner`) | The committed WIT and forwarding file are exactly the generator's output, and that output compiles against wit-bindgen 0.60. |
| `operations_return_lowered_values_through_generated_forwarding` (`fixtures/session/component`) | Calls through the generated forwarding return the expected binding values for every rule, private fields, a `&mut self` method keeping state, a struct-like case and nested `Result`/`Vec`/`Option` in generic carriers. |

Verified by hand, not by a retained test:

- The fixture builds for `wasm32-unknown-unknown`, packages with
  `wasm-tools component new`, and runs under jco 1.40 on Node 24: the factory
  returns a handle, the selection persists across calls, and results and
  failures arrive with the values the native test asserts.
- The component test fails when lowering ignores a rule or the forwarding stops
  calling an operation, and `generate --check` reports the edited file.
- A contract that disagrees with an owner type is a compile error naming the
  binding type and the parts it received.
- Adding a field to an owner type and nothing else: the check reports the WIT
  as stale, the stale component does not compile, and after regenerating the
  WIT has the field with its documentation and the component builds. The
  forwarding file did not change.

Against the acceptance criteria: criteria 1 to 3 hold end to end on the fixture,
and the mechanism of criterion 4 is in place: a field changed in its owning
type changes the WIT, the bindings and the conversion on regeneration, with no
other edit. Criterion 5 on the workbench is Phase 5.

#### Change to a Phase 3 rule

`#[wit(with = function)]` is now written `#[wit(into = W, with = function)]`,
and a computed field names its type: `field(name = "…", into = W, with = …)`.
The lowering needs the wire type as a type, and Rust cannot name the return
type of a function given only its path. The Phase 3 spike wrote that type by
hand and so did not expose this.

#### Forwarding spike

An uncommitted spike preceded the implementation.

Verified: a resource with `&self` and `&mut self` methods through a cell, a
constructor, a static function, a borrowed resource parameter and a factory;
wit-bindgen 0.60's naming for a named and a plain export, keyword parameters
and result paths; the binding derive applied to imported types including flags
and resources; the per-field diagnostic; a Wasm build, packaging and a run
under jco.

Limits:

- Parameters: numbers, booleans, text, lists, options and tuples of those, and
  borrowed resources. Anything else is an error when the file is generated.
- A resource handle may be a receiver, a borrowed parameter or a function's
  direct result. Nested in another type it is an error.
- The forwarding file follows wit-bindgen 0.60 (0.63 since Phase 6) and expects
  the bindings at the crate root.
- Operation paths are emitted as written and must start with a crate name or
  `crate`. A resource's Rust type is taken from the paths of its functions, so
  a resource must export at least one.
- A type that contains itself is rejected by the derive. Recursion through a
  second type is reported by the compiler as an overflow.
- An owner type with a `Drop` implementation cannot be taken apart.
- `ResourceCell` panics if a method is re-entered while a `&mut self` method of
  the same resource is running.
- `async fn` is not supported.

### Phase 5 — Build integration and qualification (done)

The workbench's component boundary is generated. Its branch
`feature/wit-reflect` holds the change and its own record,
`docs/libraries/wit-reflect-adoption.md`, with the full evidence.

- The owner crates carry 53 annotation lines behind a default-off feature, and
  three more describe `object` values. No name is set by hand.
- The handwritten WIT (232 lines) and three adapter files (302 lines) are gone.
- The nine types the workbench mapped with `with` by hand cross unchanged, from
  generated mappings and with no annotation for it.
- The five `Session::inspect` scenarios ran against the production component
  under jco 1.42: the successful report equals the frozen output of the
  handwritten adapter, and the failures carry the same messages in the shape
  of the Rust types.
- A field renamed in its owning type reached the WIT, the TypeScript
  declaration and the lines that read it, with no conversion code edited
  (criterion 4). The handwritten boundary is removed (criterion 5).

Findings for this library:

- jco 1.40 declares the record of a struct-like case and the case itself under
  one TypeScript name, which TypeScript merges silently. jco 1.42 inlines the
  case. The default payload name `<variant>-<case>` is unchanged.
- Hand-set names exist only to differ from the Rust name. A `name` that
  restated the derived one had gone unnoticed in the fixture.

Not verified there: the browser path with the native service, and several
acquisition failures in one inspection.

### Phase 6 — Unchanged types and wit-bindgen 0.63 (done)

Types the bindings can use as they are cross without conversion.

- `Lower::Passage` says how a type crosses. The derive answers what it can see
  on the item; the compiler answers the rest: whether the type is `Clone` and
  `Debug`, and whether every type inside it crosses unchanged.
- An unchanged value is its own parts. Containers of unchanged values are
  returned as they are.
- `ResolvedPackage::bindings(world)` renders the bindings file with one `with`
  entry per unchanged type the world reaches.
- The forwarding file names an unchanged type by its owner path.
- `#[wit(convert)]` forces conversion; `#[wit(path = …)]` names a type that is
  not exported at its crate's root.
- The fixture and the generated files follow wit-bindgen 0.63.

| A type crosses unchanged when | Seen by |
| --- | --- |
| it is `pub` and has no type parameters | the derive |
| no rule, computed field, `transparent`, `remote` or member `name` applies | the derive |
| a struct has only `pub` fields; an enum only unit cases without explicit discriminants | the derive |
| it is `Clone` and `Debug` | the compiler |
| every type inside it crosses unchanged | the compiler |

Evidence:

| Test | What it establishes |
| --- | --- |
| `a_type_crosses_unchanged_only_if_the_bindings_can_use_it_as_it_is` (`crates/wit-reflect/tests/unchanged_types.rs`) | The decision for each condition: plain types and containers of them cross unchanged; an explicit discriminant, a private field, a type holding one, a rule, a renamed field, a generic type, a type that is not `Clone`, `convert`, a case with a payload and a box are converted. |
| `committed_artifacts_are_what_the_schema_generates` (`fixtures/session/owner`) | The committed bindings file is the generator's output, next to the WIT and forwarding file, and compiles against wit-bindgen 0.63. |
| `operations_return_lowered_values_through_generated_forwarding` (`fixtures/session/component`) | An unchanged record is returned as the owner type; an unchanged enum arrives inside a converted generic carrier; a rule produces an unchanged value. The type annotations compile only while the bindings use the owner types. |

Verified by hand, not by a retained test:

- The decision test fails when the discriminant condition is removed.
- The fixture builds for `wasm32-unknown-unknown`, packages with
  `wasm-tools component new` 1.251 and runs under jco 1.40 on Node 24:
  unchanged and converted values arrive as the native test asserts them.
- With the type mappings missing from the bindings, the compiler names each
  affected pair, for example "`native::StepKind` cannot be assembled from the
  wire parts `session_owner::StepKind`".

#### Spike

An uncommitted spike on a copy of the repository preceded the implementation.

Verified:

- The Phase 4 tests pass against wit-bindgen 0.63 without a change to the
  generated forwarding.
- A passage computed through associated types compiles for records, enums,
  containers and generic carriers, and a mismatch is still reported per type.
- wit-bindgen accepts the `with` entries from a generated `macro_rules!`
  wrapper, together with `additional_derives` or with
  `additional_type_attributes`.
- Whether a concrete type is `Clone` and `Debug` can be read at compile time,
  so a type that is not is converted instead of failing in the bindings.

Findings:

- wit-bindgen lowers a mapped enum with `clone()` and a cast. That confirms
  both the `Clone` requirement and the discriminant condition.
- wit-bindgen still emits its own definition of a mapped type in an exported
  interface. Nothing refers to it.
- `with` rejects generic arguments in 0.60, 0.63 and on its main branch. A
  type alias is accepted.
- A `with` entry for a type the world does not contain is an error, so the
  entries are limited to the interfaces the world reaches.

Departures from the plan:

- The plan named a trait `Every` over a list of markers. `Passage::And`
  combines two answers instead and needs no extra bounds in generic code.
- The plan attached `FromParts` to converted types only, through
  `additional_type_attributes`. The bindings file keeps `additional_derives`.
  It needs no list of types, and the derive on an unused definition is
  harmless.
- The plan had a generated check that an unchanged type is `Clone` and
  `Debug`. The compile-time answer made it unnecessary.

Limits:

- Generic types and enums whose cases carry data are always converted.
- An unchanged type is named at its crate's root unless it declares `path`. A
  path that does not resolve is a compile error in the component crate, not
  at the declaration.
- A raw-identifier field such as `r#type` makes its struct converted, because
  the bindings spell a keyword differently.
- Inside a converted parent, a list or option of unchanged values is rebuilt
  element by element. The standard library usually reuses the allocation.
- An unchanged enum is supported in results. Parameters remain limited as in
  Phase 4.
- `generate_bindings!` sets `world`; passing `world` again is an error from
  wit-bindgen.

### Phase 7 — Declaring the contract in the Rust sources (done)

Each item states its own part of the contract and registers itself. What no
Rust item can state is read from the component crate's `Cargo.toml`. A
generator program declares nothing.

- `#[wit(interface = "…")]` on a derived type or resource registers it in that
  interface.
- `#[export(interface = "…")]` registers a free function.
- `#[exports]` on an `impl` block registers the functions marked `#[export]`.
- `#[named]` on a type alias registers the name of the instantiation.
- `Schema::from_registry` applies every registration linked into the program,
  in the order of their source positions.
- `Schema::name_instantiation` and `Schema::resource_method` accept a
  declaration before or after the interface it belongs to.
- `tasks::generate`, `tasks::check` and `tasks::run` read
  `[package.metadata.wit-reflect]` and write or check the three files. They
  are behind the `tasks` feature.

The explicit `Schema` builder is unchanged, and the registry is built on it.

| Setting in `Cargo.toml` | Meaning |
| --- | --- |
| `package`, `world` | The WIT package and the world's name. |
| `imports`, `exports` | The world's items. An export may carry its own name. |
| `wit`, `bindings`, `forwarding` | Output paths; they default to `wit/<world>.wit`, `src/bindings.rs` and `src/forwarding.rs`. |
| `[[function]]` | A function the component crate implements itself, which therefore cannot register. |

Evidence:

| Test or check | What it establishes |
| --- | --- |
| `committed_artifacts_are_what_the_declarations_generate` (`fixtures/session/owner`) | The fixture declares its contract by marks and settings only. Its three committed files did not change by one byte against the files the schema function generated. |
| `marked_items_declare_the_package_a_schema_program_would` (`crates/wit-reflect/tests/registry.rs`) | Marks and a schema program resolve to the same package, including the paths the forwarding calls. The fixture registers a resource's functions before the resource and a name after its use, marks one function through `cfg_attr`, and leaves one mark's condition false. |
| `declarations_that_fit_nowhere_are_reported` (same file) | A function of a resource that no interface declares, and a type under two names, are errors and not dropped. |

Verified by hand, not by a retained test:

- The fixture builds for `wasm32-unknown-unknown`. Its dependency tree on that
  target contains neither `inventory` nor `toml`, and `wasm-tools component new`
  1.251 packages it with the same world as before.
- A generator that names nothing from the owner crate collects no
  registration and fails with the message that says so.
- A manifest with a missing key, a misspelled key, a value of the wrong type
  and an incomplete `[[function]]` entry is rejected with all four problems
  in one report.
- Two `[[function]]` entries, one returning a resource and one returning a
  named instantiation, appear in the WIT with their documentation, and the
  forwarding calls them by the stated path. A result name that no registered
  type has is reported.
- `check` on a manifest whose files do not exist names all three as stale and
  writes nothing; `generate` then creates them with their directories.

Not run: the jco scenario of Phase 6. The generated files are unchanged and
the owner crate's code on Wasm is the same, so it was not repeated.

#### Spike

An uncommitted spike on a copy of the repository preceded the implementation.

| Check | Result |
| --- | --- |
| A registration submitted in one crate is collected in another crate's program, through `inventory` re-exported by this library | passes |
| Registrations survive when the program uses nothing else of the crate | only if the program names the crate, for example `use owner as _;`; without that the crate is not linked and nothing is collected |
| A crate reached only through another crate keeps its registrations | passes |
| A registration at module level reaches a method's reflection by the type's path | passes |
| The owner crate builds for Wasm with nothing registered | passes |

Run on macOS, debug and release. Linux and Windows are not verified.

Departures from the plan:

- The plan promised a generator of one call. It needs one `use owner as _;`
  line as well. `Schema::from_registry` fails when nothing is registered, so a
  missing line cannot yield an empty contract.
- The plan rendered interfaces in the order of `exports`. They are rendered in
  the order their first item is registered, which keeps the fixture's files
  unchanged.
- Registrations are ordered by package name before file and line. A file path
  alone differs between machines for a crate outside the workspace.
- `tasks::run` was added: the `--check` handling every generator would repeat.
- `Settings` is not public. The tasks are the API; the table is its input.

Limits:

- A marked operation is exported. Forgetting `#[exports]` on a block removes
  its functions from the contract; the check then reports the committed WIT
  as stale.
- The registry holds one contract per program. Two components need two
  generator programs, or the explicit builder.
- Definitions follow source position, so moving an item can reorder the WIT
  without changing its meaning.
- A registered operation is called at its crate's root, `owner::function` or
  `owner::Type::function`, unless `path` names another place. A wrong path is
  a compile error in the component crate.
- A `[[function]]` entry takes no parameters and names its result by WIT name.
  Its strings are leaked, once per generator run.
- `#[exports]` recognizes a mark by its last path segment, `export`, also
  inside `cfg_attr`. An attribute of another crate with that name would be
  taken for it.
- A generic type cannot name an interface, and an alias with parameters cannot
  be marked.

Examined and not adopted, 2026-11-21:

- **Interfaces named after crates.** The derive knows its crate, so a type
  could be placed without `interface`. The crate layout would then be part of
  every type's identity in the contract, helper crates would appear as
  interfaces, and one crate could not feed two interfaces. The marks stay.
- **Names composed from type arguments.** `Outcome<StepOutcome<…>>` would need
  no mark, at the price of names such as
  `outcome-step-outcome-step-kind-binary-report-inspection-failure`. Rejected:
  an instantiation is named by a marked alias.

### Phase 8 — Declarations grouped above the item (done)

A type gated behind a feature carried one wrapped attribute per rule, some of
them on its fields, and a block one wrapped mark per exported function. The
rules and the exported names can now be stated once, above the item.

- `#[exports(a, b)]` on an `impl` block names its exported functions. The
  functions need no mark of their own. A listed function is given the
  `#[export]` mark by the block attribute, so both forms share the reflection
  and its checks.
- `#[wit(skip(a, b))]` on a struct names the fields that are not exported.
- `#[wit(display = "name")]` on an item is the short form of
  `field(name = "name", into = String, with = ToString::to_string)`.

The per-function `#[export]`, the per-field `#[wit(skip)]` and the long
`field(…)` form remain.

Evidence:

| Test or check | What it establishes |
| --- | --- |
| `committed_artifacts_are_what_the_declarations_generate` (`fixtures/session/owner`) | The fixture uses the list, `skip(…)` and `display = "…"`. Its three committed files did not change by one byte. |
| `marked_items_declare_the_package_a_schema_program_would` (`crates/wit-reflect/tests/registry.rs`) | The per-function marks still register, also through `cfg_attr`. |

Verified by hand, not by a retained test. Each of these is a compile error at
the place named:

| Misuse | Reported at |
| --- | --- |
| A listed name that is no function of the block | the name |
| A function both listed and marked | the name |
| A listed function without `self` | the function |
| A block that lists and marks nothing | the block's type |
| `skip(…)` naming a field that does not exist | the name |
| `skip(…)` naming a field with a rule of its own | the name |
| `skip(…)` on an enum | the first name |
| `display = "…"` on a type that is not `Display` | the derive |

Examined and not adopted, 2026-11-23:

- **A marked block exports its public functions.** No name would be written
  twice. But `pub` would then mean "in the contract" instead of "callable from
  Rust", and functions would have to be moved between blocks to suit the
  generator. A generator describes the code as written; it does not prescribe
  how to write it.
- **Private fields are not exported.** The same objection, and it would not
  reduce the declarations: a type that keeps its fields private to protect an
  invariant would need a mark to export them.
- **Skipping every field without a WIT form.** A field whose type lost its
  derive would leave the contract silently instead of failing to compile.

Limits:

- A listed function takes no options. One that needs `static`, `constructor`
  or another name is marked with `#[export(…)]` instead.
- Exported functions are registered in the order they are written in the
  block, not in the order of the list.
- `display = "…"` reports a type that is not `Display` at the derive, not at
  the attribute.

### Phase 9 — Foreign representations declared once per crate (done)

A field whose type belongs to another crate needed a rule on every field that
holds it. That rule repeats a fact about the type. A crate now states the fact
once, in a map, and its fields carry no rule.

- `representations!` declares the map: a unit struct of the declaring crate
  and one `Represents<Foreign>` implementation per entry `Foreign => Shown`.
  The orphan rule allows it because the struct is local.
- Entries stand in groups named after where their types come from. An entry
  whose path does not begin with its group's name is an error.
- `rule::DisplayText` is the shown type for a value's `Display` text. With it
  every entry has one form, a type on each side, and one mechanism, `From`.
- The derive asks the map for every field without a rule. The generated code
  holds a constant, "does the map have an entry for this field's type?", and
  the compiler selects the entry or the type itself. Nothing is looked up when
  a value crosses.
- `[package.metadata.wit-reflect] representations = "crate::…"` names the map
  for every derive of the package's library. It is read by the derive, behind
  the `representations` feature. `#[wit(map = path)]` names a map on one item.
- `usize` and `isize` are shown as `u64` and `s64` without a rule. There is
  one lossless answer, so nothing is left to declare.

| Rule | |
| --- | --- |
| A rule on a field | wins over the map |
| A type the map does not name | is not covered; without a derive it is a compile error, as before |
| `Option<T>`, `Vec<T>` | covered by the entry for `T` |
| Case payloads and fields of struct-like cases | covered like struct fields |
| A type with an entry and a derive | the entry wins |
| A type whose fields have no entry | crosses as it would without a map, unchanged if it qualifies |

Evidence:

| Test or check | What it establishes |
| --- | --- |
| `committed_artifacts_are_what_the_declarations_generate` (`fixtures/session/owner`) | The fixture names its map in its manifest and lost four field rules and one payload rule. Its three committed files did not change by one byte. |
| `a_declared_map_represents_foreign_types_wherever_they_appear` (`crates/wit-reflect/tests/representation_rules.rs`) | A map covers a foreign type as a field, in `Option` and `Vec`, as a case payload and in a struct-like case. A rule on a field wins, and a type the map does not name is left alone. |
| `a_type_crosses_unchanged_only_if_the_bindings_can_use_it_as_it_is` (`crates/wit-reflect/tests/unchanged_types.rs`) | A type with a covered field or a `usize` field is converted. A type whose fields have no entry still crosses unchanged. |
| `ruled_owner_types_render_their_declared_wire_shapes` (`crates/wit-reflect/tests/representation_rules.rs`) | A bare `usize` field is shown as `u64`, like one with `widen`. |
| `operations_return_lowered_values_through_generated_forwarding` (`fixtures/session/component`) | Values of covered fields arrive converted through generated forwarding. |

Verified by hand, not by a retained test:

| Case | Result |
| --- | --- |
| A foreign field without an entry | compile error at the field, with a note naming the map; a second report at the derive |
| An entry whose conversion does not exist | compile error at the entry's shown type |
| Two entries for one type | compile error at the second entry |
| An entry in the wrong group | compile error at the entry |
| `map` on a generic item | compile error at the attribute |
| A `usize` parameter of an exported function | compile error at the parameter |
| The setting changed to a path that does not exist | the crate is rebuilt and every derive reports the missing type |
| A crate without the `representations` feature | its dependency tree has no TOML parser |
| The fixture for `wasm32-unknown-unknown` | builds |

Build time of the fixture's owner library, debug, three runs each: 0.22 s
with field rules, 0.23 to 0.27 s with the map. The crate has 14 derived
types; a large crate was not measured.

#### Spike

An uncommitted spike on a copy of the repository preceded the implementation.

| Check | Result |
| --- | --- |
| Generated code selects the entry or the type itself per field, across crates | works |
| The fixture with field rules replaced by a map | generated files unchanged |

| A type whose fields have no entry | still crosses unchanged |
| A macro reads a setting from the owner crate's manifest | works |
| Cargo rebuilds when only that setting changes | no; it does once the expansion includes the manifest as a tracked input |

Departures from the plan:

- The setting is applied only where `CARGO_BIN_NAME` is unset and the crate
  name is the library's. A binary can share the library's name.
- The tasks accept `representations` in the same manifest table, so that a
  component crate may hold contract settings and a map setting together.

Limits:

- A generic item uses no map: a constant expression cannot mention a type
  parameter. A foreign field there takes a rule. Naming a map on a generic
  item is an error; the crate's setting just does not reach it.
- An entry for `T` covers `Option<T>` and `Vec<T>`, not `Result`, tuples or
  `Box`.
- A field no longer shows how it is represented; the map does. The generated
  WIT shows the result.
- One setting per package, for its library target. Other targets of the
  package, and another map, use `#[wit(map = …)]`.
- A path in the setting that does not resolve is reported at every derive of
  the crate, not at the manifest.
- An uncovered field is reported at the field and a second time at the
  derive.
- `usize` is no longer flagged. A platform-sized number crosses without
  anyone writing a rule; the value is exact. An exported function cannot
  take one as a parameter, and an alias of `usize` in a parameter fails only
  when the component crate compiles.
- With the `representations` feature every derive reads the manifest once per
  crate and includes it as a tracked input.

### Phase 10 — Conversions stated in the map (done)

A map entry needed `impl From<Foreign> for Shown`. Where several foreign types
are shown as one type in the same way, that implementation was repeated for
each of them. It cannot be written once: the types of a dependency often have
functions of the same name without sharing a trait. An entry now states its
conversion, and several types share the entry.

- `Foreign => Shown with conversion` states the conversion in the map. No
  `From` implementation is written.
- `A | B => Shown` lists several foreign types in one entry. A stated
  conversion is then written once for all of them.
- The conversion is `|value| expression`, with one untyped name, or the path
  of a function that takes the value. The macro makes the expression the body
  of one function per foreign type, with the value typed as that type. A real
  closure would have to infer the type, which fails for a method call.
- The expression is checked once per foreign type. The types need only the
  functions it calls.
- An entry without `with` converts through `From`, as before.
- A stated conversion also connects two types of other crates, such as
  `std::time::Duration => u64`. The orphan rule forbids that `From`
  implementation, so the map could not express it before.

| --- | --- |
| `committed_artifacts_are_what_the_declarations_generate` (`fixtures/session/owner`) | The fixture states its one conversion in the map and lost its `From` implementation. Its three committed files did not change by one byte. |
| `operations_return_lowered_values_through_generated_forwarding` (`fixtures/session/component`) | A value converted by a stated conversion arrives through generated forwarding as before. |
| `a_declared_map_represents_foreign_types_wherever_they_appear` (`crates/wit-reflect/tests/representation_rules.rs`) | One conversion serves two types that share no trait, and another connects two types of other crates. |

- The conversion sees one value. A value that depends on a sibling field
  still takes a rule on that field.
- The types of one entry stand in one group, so they come from one crate.
- A stated conversion is not a `From` implementation. A field rule
  `into = Shown` on such a type still needs one.

### Phase 11 — Only a root states an interface (done)

Two statements said what a function already says. A resource had to state its
interface, although the function that returns it states one. And a function
that only the component crate can implement was declared in that crate's
manifest, as a signature written by hand, because the component crate cannot
register anything.

The rule that covers both: only a root states an interface. A root is a
function of an interface, or a type or resource that nothing else places.
Everything a root mentions follows it.

- A resource that no interface declares belongs to the only interface that
  reaches it, as any other type does. Its own functions can reach another
  resource, so placing repeats until nothing more is placed.
- `#[exports(interface = "…", a, b)]` on a trait registers the listed
  functions as functions of that interface. Their signatures are reflected by
  the code that reflects `#[export]`.
- The component crate implements the trait for the `Component` type of its
  generated forwarding, without a mark. The forwarding calls
  `<Component as owner::Trait>::function(…)`.
- A trait's function is a free function whose path names the trait. The
  resolution of functions, the rendering and the settings did not change.
- A `function` entry in the manifest keeps working.

Evidence:

| Test or check | What it establishes |
| --- | --- |
| `marked_items_declare_the_package_a_schema_program_would` (`crates/wit-reflect/tests/registry.rs`) | A resource without a mark is placed by the function that returns it. A trait's listed function is registered with the path through the trait, and an unlisted one is not exported. Both equal what a schema program lists. |
| `declarations_that_fit_nowhere_are_reported` (same file) | A resource that nothing reaches is still reported. |
| `committed_artifacts_are_what_the_declarations_generate` (`fixtures/session/owner`) | The fixture's resource lost its mark, which changed none of its three files. Its new trait adds one function to the WIT and one call through the trait to the forwarding. |
| The fixture component compiles and `operations_return_lowered_values_through_generated_forwarding` passes | The generated call through the trait compiles against the component's implementation. |

Verified by hand, not by a retained test:

| Case | Result |
| --- | --- |
| A resource reached only through a function of another placed resource | placed in the same interface |
| A resource that two interfaces reach | one error, naming both interfaces |
| A trait function that takes `self` | compile error at the receiver |
| A trait without an interface, or without a listed function | compile error at the trait |
| A listed name the trait does not have | compile error at the name |
| A generic trait | compile error at the type parameter |
| `interface` on an `impl` block | compile error at the option |
| A component that does not implement the trait | compile error in the generated forwarding, naming the trait |

An uncommitted trial on copies of this repository and of the workbench
preceded the implementation. In the workbench copy the resource's mark and the
manifest's function entry were removed. Its WIT and bindings files did not
change, one line of its forwarding file did, and the component built for
`wasm32-unknown-unknown`.

Limits:

- Interfaces appear in the order in which they are first stated. Removing a
  resource's mark moves its interface later if that mark stated it first.
- A resource that nothing reaches, or that several interfaces reach, still
  states its interface.
- A trait function takes no `self`, and the implementing type is always the
  forwarding's `Component`.
- The trait is named at its crate's root unless `path = …` says otherwise.
- The registration of a trait's functions is not compiled for Wasm targets;
  the reflection of their signatures is.

## Alternatives to the derive, examined and not adopted

The derive exists because a macro sees only the item it is attached to. Three
ways to read a type without it were measured against the workbench and the
`object` crate. None is adopted.

### Compile-time reflection (`#![feature(type_info)]`)

Probed on `nightly-2026-11-21` (rustc 1.102.0-nightly) with no derive on the
types. It is the only route that describes a type of another crate without
that crate's cooperation and with the compiler's own name resolution.

A prototype started from the two result types of the workbench's session
operations and followed fields. It described all 28 contract types with
correct fields, cases, generic arguments and doc comments. It also walked into
19 internal or foreign types, each of which a rule excludes or reshapes today.

| It reports | Probe result |
| --- | --- |
| Cases of a foreign enum, with their doc comments | `object::Endianness`: `Little`, `Big` and the documentation of each |
| Fields of a struct: name, type, offset, doc comment | every field of the workbench's report types |
| Width and sign of integers | `u32` and `i64` told apart |
| Whether a type implements a trait that can be a trait object | `object::macho::Version`: `Display`; `object::Endianness`: `Debug` but not `Display` |
| Attributes of a registered tool, as text | `#[wit::display]` on a field |
| `#[non_exhaustive]`, generic arguments, pointers, arrays | reported |

| It does not report | State upstream | Effect |
| --- | --- | --- |
| A type's name from its `TypeId` | rust-lang/rust#164981 adds `TypeId::name`; approved, waiting for a rebase | It returns the bare item name, such as `Vec` for `Vec<T>`. That names a WIT definition. It gives no crate and no path. |
| Discriminant values | partly in rust-lang/rust#165141, changes requested | An enum with explicit discriminants cannot be told from a plain one. |
| The case of an enum value at run time | the same pull request | Enum values cannot be read by reflection. |
| Field visibility | none found | Private fields look like public ones. |
| Methods and functions | none found | A representation built from a method, and the exported operations, cannot be derived. |
| Whether a type is `Clone` | not expressible; `Clone` cannot be a trait object | The condition for crossing unchanged cannot be checked this way. |
| Attributes of tools the defining crate did not register | by design | Only this library's own attributes are readable. |

Walking nested types needs no internal feature. A function that receives a
`TypeId` may not call the reflection methods, because it could run at run
time. The same loop written in the initializer of a constant compiles, and a
`macro_rules!` macro can expand it.

#### Field-representing types

A second nightly feature gives what `type_info` lacks: a route from a type to
the types of its fields at the type level.
`<FieldRepresentingType<T, VARIANT, FIELD> as Field>::Type` is the type of a
field chosen by position, and `Field::OFFSET` is its byte offset.

| Probe | Result |
| --- | --- |
| `BinaryReport`, field 0 | `binary_inspection::model::ContainerKind` |
| `BinaryReport`, field 1 | `object::endian::Endianness` |
| A private field of a type in another crate | its type, in full |
| A field of an enum case | rejected: `Field` is not implemented, because the field does not exist in every value |

It yields full paths today, so a struct's nested types can be named and their
crate told apart without `TypeId::name`. A path names the defining module,
which may be private, so it is not always one that other code can write. With
the offset, a conversion of structs without a derive is conceivable. It needs
`field_projections`, which the compiler reports as incomplete and possibly
unsafe, and the compiler-internal `field_representing_type_raw`.

#### What a contract generated by reflection alone would still need

| Need | State |
| --- | --- |
| Describe every type | works |
| Name every definition | after rust-lang/rust#164981 |
| Convert struct values | conceivable through field-representing types; not built |
| Convert enum values | not possible; five of the 28 contract types are enums whose cases carry data, and nine types contain one |
| Decide what is not part of the contract | a person's decision, expressed as rules |
| Describe the exported operations | marks on the operations, since methods are not reflected |

Six unstable features would be involved: `type_info`, `field_projections`,
`field_representing_type_raw`, `const_cmp`, `const_trait_impl`, and
`register_tool` if rules are read as attributes. `type_info` changed five times
between 2026-11-12 and 2026-11-20; doc comments arrived one nightly before the
probe, and `Type::of` was removed the day before it. The tracking issue,
rust-lang/rust#146922, has no RFC and lists whether to do this at all as an
open question.

What it would replace, in the order it becomes possible: a `remote`
declaration of a plain foreign enum, whose cases and documentation it reports
in full; then, once names are available, the description of every type and
with it the derive on types that cross unchanged. It would not replace the
conversion of enums, the rules or the marks on operations.

### The compiler's JSON output (`rustdoc --output-format json`)

Read for `binary-inspection` on a nightly from June 2026. It contains type
names, doc comments, visibility and field types resolved through re-exports,
which closes reflection's naming gap. It needs nightly for generation, its
format is versioned and unstable, and conversion would have to be generated
into the component crate, where private fields are out of reach.

### Reading source files with `syn`

`syn` parses text on stable Rust. On `object` 0.40 it read `Endianness` with
its documentation. It did not find `FileType`, which `object` defines through
its own macro: `syn` expands no macros and resolves no paths, so a generator
built on it would have to redo that work of the compiler.

## Open points for later phases

- An experimental nightly backend that describes types by reflection, once
  `TypeId::name` is available. It would first replace `remote` declarations of
  plain foreign enums and the derive on types that cross unchanged.
- Whether the workbench needs records or enums as inputs, which would require
  lifting.
- Unchanged crossing for enums whose cases carry data, and for generic types
  through a type alias.
- Asynchronous exports under JSPI, which the workbench's bindings enable.
- A representation map for generic items, and for containers other than
  `Option` and `Vec`.
- A map entry for a type inside its owner, for a value whose meaning depends
  on its neighbour. It was tried and not added; see
  [the issue](issues/neighbour-dependent-value.md).
